# Plan de validación

## Hipótesis principal

Los equipos indie multidisciplinares que ya usan GitHub adoptarán una capa de briefing/atención si les ahorra el tiempo de reconstruir contexto tras una ausencia y les muestra bloqueos por impacto.

## Preguntas a validar

1. ¿La landing se diferencia de un Kanban genérico?
2. ¿El briefing “desde la última visita” se percibe como verdadero?
3. ¿La cola de atención prioriza lo que el equipo considera urgente?
4. ¿Las personas no técnicas entienden PRs, CI y bloqueos con el copy actual?
5. ¿Conectar GitHub se siente como el primer paso natural (antes que crear tareas)?
6. ¿El modo demostración transmite el valor sin confundirse con datos reales?

## Métodos

| Método                                         | Cuándo                        | Muestra                       |
| ---------------------------------------------- | ----------------------------- | ----------------------------- |
| Revisión de landing (5 segundos + 30 segundos) | Tras rewrite de copy          | 5–8 personas del perfil indie |
| Recorrido guiado del modo demo                 | Tras Fase C/D                 | 3–5 equipos pequeños          |
| Prueba de briefing con repo real               | Cuando App + env estén listos | 2–3 proyectos voluntarios     |
| Checklist a11y + teclado                       | Cada superficie nueva         | Automatizado + pase manual    |

## Criterio para iterar o pivotar

- Si más de la mitad describe HubForge como “otro Trello/Jira”, reescribir posicionamiento.
- Si el briefing se percibe como contadores, reforzar hechos + “por qué importa” + acción.
- Si nadie conecta GitHub en el onboarding, adelantar aún más la instalación de la App.

## Estado

Validación de producto **pendiente** de las superficies reposicionadas. Este documento no afirma tracción ni usuarios activos.
